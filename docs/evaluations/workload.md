# Portable-device workload contract

The readiness campaign uses one deterministic, small artifact so every route
is judged against the same bytes. The contract is recorded in
[`workload.json`](workload.json) and generated by
[`experiments/device_readiness/fixtures.py`](../../experiments/device_readiness/fixtures.py).
It contains named language, speech input, speech output, vision and specialist
tensors, plus a 96 KiB tensor that deliberately exceeds the 32 KiB stream
target. The tensor roles make route and consumer accounting possible without
pretending that the fixture is an ASR, TTS, vision or language benchmark.

Contract schema 2 records synthetic provenance, repository license
applicability, the absence of required sidecars, parser/runtime compatibility,
and the boundary between transport evidence and a real consumer. Plain bytes
are always available; stdlib-coded and optional lmz-coded routes retain their
capability reason when unavailable. Every role uses seed 7 with a fixed input
hash and exact output hash. No audio, image, prompt or real application
acceptance fixture is available.

The plain artifact is 145,012 bytes: a 628 byte header and 144,384 bytes of
tensor data. Its SHA-256 is frozen. The stdlib-coded archive carries the same
plaintext contract, but its container includes measured codec metadata, so its
container hash is recorded per run rather than treated as a portable identity.
The low-compressibility binary is a separate link fixture and is not part of
the named tensor output contract.

The campaign checks both transport bytes and consumer-visible output. A full
load must reproduce the plain artifact hash; selected and streamed loads hash
the exact tensor bytes in file order. A matching hash establishes byte
preservation for this fixture. It does not establish application quality,
latency for a real voice interaction, or suitability for a particular device.

Each run reports planned and actual routes, codec and cipher availability,
logical/coded/transferred/fetched/placed bytes, coverage, worker settings and
bounded process resource samples. Readiness events share one monotonic clock:
source open, route planning, allocation, staging, first payload, first tensor,
transfer completion, first useful consumer output, consumer ready and terminal
failure. A consumer owns the useful and ready marks; missing marks remain
`null`.

The default campaign keeps caches off for loader arms and records whether a
true host-cold read was controllable. It uses one shared 96 KiB/s synthetic
limiter while comparing one and two fetch workers, so concurrency cannot be
mistaken for additional link capacity. The fixtures, keys and local HTTP
servers stay inside a fresh run directory; no external store or credential is
required.
